**# Отчёт по практической №1 — Lakehouse, вариант Q3**



**## 1. Вариант и масштаб**



\| Поле | Значение |

\| ФИО (как в VK Education) | Козлова Виктория |

\| Вариант (запрос) | Q3 — Shipping Priority |

\| Масштаб \`sfN\` | sf1 |

\| Почему выбрал такой масштаб | Выбран SF1, потому что это базовый масштаб TPC-H, подходящий для проверки полного цикла загрузки и обработки данных на локальном компьютере. Он позволяет сравнить слои Bronze, Silver и Gold, не создавая чрезмерную нагрузку на систему. |



**## 2. Поднятые сервисы — и почему именно они**



Используется пример \`examples/minimal\` из репозитория Lakekeeper. Сервисы и их фактическое состояние необходимо проверить командой \`docker compose ps\` после успешного запуска.



\| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |

\|---|---|---|

\| Silo | S3-совместимое объектное хранилище для файлов таблиц | В текущем примере Lakekeeper Silo предоставляет S3 API и используется как хранилище объектов. Это не оригинальный MinIO, поэтому подмена явно указана. Если по требованиям преподавателя нужен строго MinIO, конфигурацию необходимо заменить. |

\| PostgreSQL | База данных метаданных Lakekeeper | Хранит служебные метаданные каталога. Это распространённая реляционная СУБД с открытым исходным кодом. |

\| Lakekeeper | Iceberg REST Catalog | Управляет каталогом таблиц Apache Iceberg и предоставляет REST API для движков обработки данных. |

\| Trino | SQL-движок | Позволяет выполнять SQL-запросы к источникам и таблицам Lakehouse, создавать таблицы и выполнять аналитические преобразования. |

\| Jupyter / Spark | Среда для работы с данными | Даёт возможность исследовать и обрабатывать данные с помощью Python и Spark. |

\| StarRocks | Дополнительный аналитический движок | Входит в пример минимального стенда и может использоваться для дополнительной проверки аналитической работы с данными. |



**### Скрипты, которыми поднимался стек**



Команды выполняются из каталога \`lakekeeper-demo/examples/minimal\`. Пока Docker Desktop выдаёт ошибку файловой системы, нельзя утверждать, что все сервисы успешно запущены.



\`\`\`bash

\# Проверить конфигурацию Compose

docker compose config --quiet



\# Запустить сервисы в фоновом режиме

docker compose up -d



\# Проверить, какие контейнеры реально запущены

docker compose ps

\`\`\`



**## 3. Разбор запроса — какие данные нужны**



Вариант Q3 (Shipping Priority) рассчитывает выручку по заказам клиентов сегмента \`BUILDING\`, применяет ограничения по датам заказа и отгрузки, группирует результат по заказу и сортирует его по выручке.



\| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |

\|---|---|---|

\| \`customer\` | \`custkey\`, \`mktsegment\` | \`custkey\` соединяет клиента с заказами; \`mktsegment\` фильтрует клиентов по сегменту \`BUILDING\`. |

\| \`orders\` | \`orderkey\`, \`custkey\`, \`orderdate\`, \`shippriority\` | \`custkey\` используется для соединения с \`customer\`; \`orderkey\` — с \`lineitem\`; \`orderdate\` фильтрует заказы и выводится в результате; \`shippriority\` выводится и участвует в группировке. |

\| \`lineitem\` | \`orderkey\`, \`extendedprice\`, \`discount\`, \`shipdate\` | \`orderkey\` соединяет позиции с заказами; \`extendedprice\` и \`discount\` используются для вычисления выручки; \`shipdate\` применяется в фильтре. |



**## 4. Медальон — решения по каждому слою**

**## 5. Тесты производительности**



Для примера сравнения использован один и тот же объём Bronze и одинаковый аналитический запрос. Значения ниже являются демонстрационными: при реальном запуске время и размер нужно заменить результатами своего стенда.



\| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |

\|---|---:|---:|---|

\| GZIP | 4,82 с | 544,5 | В примере GZIP занимает больше места и выполняет запрос медленнее, чем ZSTD. |

\| ZSTD | 3,17 с | 510,0 | В примере ZSTD уменьшает размер примерно на 6,3% и сокращает время запроса примерно на 34%; для этого сценария он предпочтительнее. |







**## 6. Часть 2 — осмысление и работа с инструментами**



**### 6.1. Понять и объяснить**



\| Вопрос | Твой ответ |

\|---|---|

\| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse объединяет хранение данных в объектном хранилище и возможности аналитической работы с таблицами. Это позволяет хранить большие объёмы данных в открытых форматах и выполнять SQL-запросы через отдельный движок, например Trino. В отличие от обычной транзакционной БД, архитектура ориентирована на аналитические нагрузки и работу с файлами в объектном хранилище. |

\| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Schema evolution — изменение схемы таблицы, например добавление нового столбца. В Iceberg схема и её версии описываются метаданными таблицы. Поддерживаемая операция выполняется через SQL-движок, а изменения схемы регистрируются в метаданных; точный синтаксис зависит от версии Trino и каталога. Пример для проверки после запуска: \`ALTER TABLE lakehouse.default.silver_customer ADD COLUMN source_system varchar;\`. |

\| Пример скрипта восстановления данных из снапшота (time travel) | Iceberg хранит снимки состояния таблицы. Через поддерживаемые движком операции можно обратиться к прошлому снимку и восстановить предыдущее состояние. Конкретная команда восстановления зависит от версии Trino и каталога, поэтому перед сдачей нужно проверить поддерживаемый синтаксис на установленной версии, а не запускать неподтверждённую команду. |



**### 6.2. Подключить инструмент к lakehouse**



\| Инструмент | Почему выбрал именно его |

\|---|---|

\| Trino | Trino уже входит в минимальный пример Lakekeeper и предназначен для выполнения SQL. Он подходит для демонстрации чтения Bronze и создания Silver/Gold без добавления ещё одного сервиса. |



После успешного запуска приложить скриншот выполнения запроса к таблице Bronze, например:



\`\`\`sql

SELECT \* FROM lakehouse.default.bronze_customer LIMIT 10;

\`\`\`



Также приложить команды запуска из раздела 2 и вывод \`docker compose ps\`. Скриншот взаимодействия можно сделать только после реального запуска стенда.



**## 7. Выводы**



В работе рассматривается построение Lakehouse для аналитического запроса TPC-H Q3. Медальонная архитектура разделяет исходные данные Bronze, подготовленные данные Silver и итоговую витрину Gold. Parquet выбран как колоночный формат для аналитики, а Snappy и ZSTD рассматриваются как варианты сжатия, которые нужно сравнить измерениями. Для демонстрационного расчёта в таблицы внесены ориентировочные значения: Bronze хранит исходные данные, Silver использует ZSTD и сокращённый набор полей, а Gold содержит итоговые 10 строк запроса Q3. В реальном запуске размеры и время могут отличаться.
